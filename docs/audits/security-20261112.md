## Remediation and classification

Direct runtime: Torch 2.9.0+cpu upgraded to 2.13.0+cpu and Torchvision 0.24.0+cpu to 0.28.0+cpu. Native NMS, full application checks and untrained inference pass. The [publisher pairs these versions](https://pytorch.org/get-started/previous-versions/).
The [new Torch advisory](https://github.com/pytorch/pytorch/security/advisories/GHSA-v32g-mr63-3j83) starts at 2.14.0 and lists 2.15.0 as patched; the chosen 2.13.0 pair is outside that stated range. This is not a claim that every Torch execution mode is safe.
Transitive runtime: setuptools constrained to 84.2.1. The old image had findings in setuptools and vendored jaraco.context/wheel, plus pip-associated vendored msgpack/urllib3 metadata. New production omits pip and ensurepip after installation; dev/test images keep their tooling. No vendored source is manually edited. Production inference verifies that removing build tools did not break the supported path.
OS: apt security updates applied during build, fixing the two old zlib high matches and one expat medium match. A rebuild still depends on the current apt repository; Python wheel hashes alone do not make the full OS build reproducible.
The old production Python scan had 17 raw matches; the new production scan has zero Python matches. Old findings and failed Grype attempts are retained, not erased.

## Highest unresolved finding

`CVE-2026-6653`, libxml2 `2.12.7+dfsg+really2.9.14-2.1+deb13u3`, is scanner CRITICAL. [Debian marks this exact trixie version vulnerable and the issue minor/no-dsa](https://security-tracker.debian.org/tracker/CVE-2026-6653); the package version deliberately contains really2.9.14. Treating the 2.12.7 prefix as a fix would be incorrect. The upstream issue describes crafted-XML use-after-free/DoS. Vendor CVSS/severity selections differ, and the scanner critical rating is preserved.
There is no application XML endpoint. That narrows the obvious attack surface but does not establish that all transitive native input paths are unreachable. No exploit test or formal reachability proof was run. Only trusted local model/media/data inputs are suitable for the current offline pilot. No owner has accepted this residual risk.

## Scanner limits and reproducibility

The previous Grype scan failed/ran past 900 seconds while loading its large DB on the Windows-mounted cache. Native Trivy avoids that container/cache path and completed the old-image scan in 210.627 seconds and the final-image scan in about 41 seconds using the cached DB. This demonstrates a practical replacement; the exact Grype internal bottleneck was not proven.
The Windows release archive SHA-256 was checked against the official GitHub release digest. The Linux CI archive also has an exact release checksum. Signature verification was not performed.
